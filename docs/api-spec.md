# KiddyBD API Specification (v1)

This is the comprehensive production-ready API specification for KiddyBD backend, aligning with `architecture.md` and `database.md`.

## 1. Global API Standards

### 1.1 Standard Response Format
All successful responses must follow this format:
```json
{
  "success": true,
  "message": "Human readable message",
  "data": {},
  "meta": {} 
}
```

### 1.2 Standard Error Format
All error responses must follow this format:
```json
{
  "success": false,
  "message": "Human readable error message",
  "error": {
    "code": "ERROR_CODE",
    "details": []
  }
}
```

### 1.3 Standard Pagination Format
When paginated, `meta` in the success response must include:
```json
"meta": {
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 100,
    "totalPages": 5
  }
}
```

### 1.4 API Guidelines & Strategies
*   **API Versioning:** Handled via URL path (e.g., `/api/v1/...`).
*   **Authentication Strategy:** Stateless JWT Bearer tokens for API access.
*   **JWT Handling:** Short-lived Access Token (e.g., 15m), sent in `Authorization: Bearer <token>`.
*   **Refresh Token Handling:** Long-lived Refresh Token stored in DB `RefreshToken` entity and sent via HTTP-Only Secure Cookie or Body.
*   **RBAC (Role-Based Access Control):** Defined via `Role` enum (e.g., `SUPER_ADMIN`, `CUSTOMER`). Validated in middleware.
*   **Request Validation:** All incoming requests validated via Zod.
*   **Rate Limiting:** Applied globally via Redis. Stricter limits on sensitive endpoints (`/auth`, `/checkout`).
*   **Idempotency:** Required for mutating financial/order operations via `Idempotency-Key` header. Tracked in `IdempotencyKey` table.
*   **Webhook Security:** HMAC SHA256 Signature verification using provider-specific secrets.
*   **File Upload Strategy:** Presigned URLs (S3) generated by backend. Client uploads directly to bucket, then sends URL to backend.
*   **Filtering/Sorting/Search:** Passed via query params (e.g., `?sort=-price&category=toys&search=lego`).

### 1.5 Major Error Codes
*   `VALIDATION_ERROR`: Invalid request payload.
*   `UNAUTHORIZED`: Missing or invalid token.
*   `FORBIDDEN`: Insufficient role/permissions.
*   `NOT_FOUND`: Resource missing.
*   `CONFLICT`: State conflict (e.g., duplicate, already processed).
*   `INVENTORY_LOCKED`: Race condition in stock.
*   `OUT_OF_STOCK`: Insufficient available stock.
*   `RISK_REJECTED`: Order blocked — high risk, COD not permitted.
*   `RISK_REVIEW_REQUIRED`: Order flagged for manual risk review.
*   `RATE_LIMIT_EXCEEDED`: Too many requests.
*   `INTERNAL_ERROR`: Unhandled server exception.
*   `OTP_EXPIRED`: OTP has expired.
*   `OTP_TOO_MANY_ATTEMPTS`: Maximum OTP verification attempts exceeded.
*   `INVALID_ORDER_STATE`: Order state transition is not permitted.
*   `PAYMENT_FAILED`: Payment processing failed.
*   `PAYMENT_VERIFICATION_FAILED`: Could not verify payment with gateway.
*   `COUPON_INVALID`: Coupon is expired, inactive, or not applicable to this order.
*   `UNAUTHORIZED_WEBHOOK`: Webhook signature verification failed.

## 2. Critical Flows

**A. Registration/Login**
Client -> API -> Request OTP -> SMS Gateway -> Client submits OTP -> API verifies -> Returns JWT & Refresh Token.

**B. Product Browsing**
Client -> API -> Fetch Products (Cached in Redis) -> Client views variants and stock.

**C. Cart**
Client -> API -> Adds Variant -> API validates existence & stock limit -> Cart updated.

**D. Checkout**
Client -> API -> Submits Cart + Address + Coupon -> API calculates server-side totals -> Returns checkout summary.

**E. Order Creation (Specific Flow)**
1. **Client** initiates `POST /orders`
2. **API** receives request with `Idempotency-Key`.
3. **Authentication & Validation:** Verify JWT, check RBAC, Zod schema check.
4. **Cart Validation:** Check if cart exists and is active.
5. **Product & Price Validation:** Fetch current DB prices (never trust client).
6. **Address & Coupon Validation:** Ensure address belongs to user, coupon is valid/applicable.
7. **Stock Validation:** Check current `Inventory.quantity - reservedQuantity`.
8. **Risk Assessment:** Run risk rules (past RTO, IP, device). Assign `RiskLevel`.
9. **COD/Payment Decision:** If High Risk, reject COD and mandate Advanced Payment or OTP.
10. **Database Transaction BEGIN:**
11. **Inventory Reservation:** Insert `InventoryReservation`, increment `Inventory.reservedQuantity`.
12. **Order Creation:** Insert `Order`, `OrderItem`s, capture address snapshot.
13. **Verification:** Create `OrderVerification` if required (e.g., OTP).
14. **Database Transaction COMMIT**
15. **Event Emission:** Publish `OrderCreatedEvent`.
16. **Response:** Return standard success with Order details.

*(F through T follow similar strict server-side validation models protecting the domain).*

## 3. Endpoints Specification

### 3.1 Auth Module

> Customer auth is **passwordless** — Phone OTP, Email OTP, or Google OAuth. Admin auth uses Email + Password.

#### 📱 Phone OTP Flow

**Endpoint:** `POST /api/v1/auth/phone/send-otp`
1. **HTTP Method:** `POST`
2. **Endpoint path:** `/api/v1/auth/phone/send-otp`
3. **Purpose:** Send OTP via SMS to customer's phone.
4. **Auth requirement:** None.
5. **Request body:** `{ "phone": "string" }`
6. **Validation rules:** Valid BD phone number (01XXXXXXXXX, 11 digits).
7. **Business rules:** Generate 6-digit OTP. Store in Redis with 5-min TTL. Enforce 60s resend cooldown per phone. Rate-limit by IP + phone.
8. **DB entities affected:** None (OTP in Redis only).
9. **Success response:** `{ "success": true, "message": "OTP sent successfully" }`
10. **Error codes:** `RATE_LIMIT_EXCEEDED`, `VALIDATION_ERROR`
11. **Rate limiting:** 3 requests / 5 minutes / phone.

**Endpoint:** `POST /api/v1/auth/phone/verify-otp`
1. **HTTP Method:** `POST`
2. **Endpoint path:** `/api/v1/auth/phone/verify-otp`
3. **Purpose:** Verify phone OTP and issue JWT. Creates account if first login.
4. **Auth requirement:** None.
5. **Request headers:** `X-Device-Id`
6. **Request body:** `{ "phone": "string", "otp": "string" }`
7. **Validation rules:** Phone valid, OTP 6 digits.
8. **Business rules:** Verify OTP in Redis. Increment attempt counter (max 5). On success: `upsert User` (find by phone, create if not exists). Issue Access + Refresh Token. Set `phoneVerifiedAt`. Clear OTP.
9. **DB entities affected:** `User`, `RefreshToken`
10. **Success response:** `{ "success": true, "data": { "accessToken": "...", "user": { "id": "...", "phone": "...", "name": "...", "role": "CUSTOMER" } } }`. Refresh token via HttpOnly cookie.
11. **Error codes:** `OTP_EXPIRED`, `OTP_TOO_MANY_ATTEMPTS`, `VALIDATION_ERROR`
12. **Rate limiting:** 5 attempts / phone.

#### 📧 Email OTP Flow

**Endpoint:** `POST /api/v1/auth/email/send-otp`
1. **HTTP Method:** `POST`
2. **Endpoint path:** `/api/v1/auth/email/send-otp`
3. **Purpose:** Send OTP to customer's email inbox.
4. **Auth requirement:** None.
5. **Request body:** `{ "email": "string" }`
6. **Validation rules:** Valid email format.
7. **Business rules:** Generate 6-digit OTP. Store in Redis with 10-min TTL. Rate-limit by IP + email. Resend cooldown 60s.
8. **DB entities affected:** None (OTP in Redis only).
9. **Success response:** `{ "success": true, "message": "OTP sent to email" }`
10. **Error codes:** `RATE_LIMIT_EXCEEDED`, `VALIDATION_ERROR`
11. **Rate limiting:** 3 requests / 10 minutes / email.

**Endpoint:** `POST /api/v1/auth/email/verify-otp`
1. **HTTP Method:** `POST`
2. **Endpoint path:** `/api/v1/auth/email/verify-otp`
3. **Purpose:** Verify email OTP and issue JWT. Creates account if first login.
4. **Auth requirement:** None.
5. **Request headers:** `X-Device-Id`
6. **Request body:** `{ "email": "string", "otp": "string" }`
7. **Business rules:** Verify OTP. On success: `upsert User` (find by email, create if not exists). Issue tokens. Set `emailVerifiedAt`. If same email already linked to a Google account, the tokens will be for that existing account (account linking).
8. **DB entities affected:** `User`, `RefreshToken`
9. **Success response:** Same shape as phone verify-otp.
10. **Error codes:** `OTP_EXPIRED`, `OTP_TOO_MANY_ATTEMPTS`, `VALIDATION_ERROR`
11. **Rate limiting:** 5 attempts / email.

#### 🔵 Google OAuth Flow

**Endpoint:** `GET /api/v1/auth/google`
1. **HTTP Method:** `GET`
2. **Purpose:** Redirect user to Google OAuth consent screen.
3. **Auth requirement:** None.
4. **Business rules:** Generate state parameter (anti-CSRF). Store in Redis. Redirect to Google with `client_id`, `redirect_uri`, `scope` (email, profile), `state`.
5. **Response:** `302 Redirect → Google`

**Endpoint:** `GET /api/v1/auth/google/callback`
1. **HTTP Method:** `GET`
2. **Purpose:** Handle Google OAuth callback, issue JWT.
3. **Auth requirement:** None.
4. **Query parameters:** `code` (authorization code), `state` (anti-CSRF)
5. **Business rules (Account Linking):**
   - Validate `state` against Redis.
   - Exchange `code` for Google tokens.
   - Extract `sub` (googleId) and `email` from Google profile.
   - Lookup by `googleId` → if found, login.
   - Else lookup by `email` → if found, link Google to existing account (set `googleId`, `googleLinkedAt`).
   - Else create new User with `googleId` + `email`. Set `emailVerifiedAt = now`.
   - Issue Access + Refresh Token.
6. **DB entities affected:** `User`, `RefreshToken`
7. **Response:** Redirect to frontend with JWT in query param or set cookie.
8. **Error codes:** `UNAUTHORIZED` (state mismatch or Google error)

#### 🔑 Admin Login

**Endpoint:** `POST /api/v1/auth/admin/login`
1. **HTTP Method:** `POST`
2. **Purpose:** Authenticate admin user with email + password.
3. **Auth requirement:** None.
4. **Request body:** `{ "email": "string", "password": "string" }`
5. **Business rules:** Find User by email. Bcrypt verify password. Role must be non-CUSTOMER. Issue short-lived Access Token.
6. **DB entities affected:** `User`, `RefreshToken`
7. **Error codes:** `UNAUTHORIZED`, `VALIDATION_ERROR`
8. **Rate limiting:** 5 requests / minute / IP.

---

#### 🔄 Token Management

**Endpoint:** `POST /api/v1/auth/refresh-token`
1. **Purpose:** Rotate refresh token and issue new access token.
2. **Auth requirement:** Valid Refresh Token (HttpOnly cookie or body).
3. **Business rules:** Validate token against DB (`revokedAt` null, `expiresAt` in future). Issue new pair. Revoke old token (set `revokedAt`).
4. **DB entities affected:** `RefreshToken`
5. **Error codes:** `UNAUTHORIZED`

**Endpoint:** `POST /api/v1/auth/logout`
1. **Purpose:** Revoke session.
2. **Auth requirement:** Required (Access Token).
3. **Business rules:** Set `revokedAt` on current `RefreshToken`. Clear HttpOnly cookie.
4. **DB entities affected:** `RefreshToken`
5. **Success response:** `{ "success": true, "message": "Logged out successfully" }`

### 3.2 Orders Module

**Endpoint:** `POST /api/v1/orders`
1. **HTTP Method:** `POST`
2. **Endpoint path:** `/api/v1/orders`
3. **Purpose:** Create a new order (Checkout).
4. **Auth requirement:** Required.
5. **Required role:** `CUSTOMER`.
6. **Request headers:** `Authorization`, `Idempotency-Key`
7. **Path parameters:** None.
8. **Query parameters:** None.
9. **Request body:** `{ "addressId": "uuid", "couponCode": "string?", "paymentMethod": "COD|ONLINE", "cartId": "uuid" }`
10. **Validation rules:** All fields required, valid UUIDs.
11. **Business rules:** Server-side price calculation, inventory reservation, risk assessment. Never trust client values.
12. **DB entities affected:** `Order`, `OrderItem`, `Inventory`, `InventoryReservation`, `RiskAssessment`, `CouponUsage`.
13. **Transaction boundary:** Strict BEGIN/COMMIT transaction. Rollback on stock/risk failure.
14. **Idempotency:** REQUIRED (Header matched against `IdempotencyKey` table).
15. **Success response:** `{ "success": true, "data": { "orderId": "...", "orderNumber": "ORD-2026-XXXXX", "total": 1500, "status": "PENDING", "paymentStatus": "PENDING", "fulfillmentStatus": null } }`
16. **Error responses:** `400 Out of Stock`, `409 Conflict`, `403 Risk Rejected`.
17. **Error codes:** `OUT_OF_STOCK`, `RISK_REJECTED`, `INVENTORY_LOCKED`
18. **Pagination:** N/A
19. **Rate limiting:** 2 requests / minute / User.

### 3.3 Payments Module

**Endpoint:** `POST /api/v1/webhooks/payment/:provider`
1. **HTTP Method:** `POST`
2. **Endpoint path:** `/api/v1/webhooks/payment/:provider` (e.g., `/bkash`, `/nagad`, `/sslcommerz`)
3. **Purpose:** Receive payment status asynchronously.
4. **Auth requirement:** None (Webhook signature validated instead).
5. **Required role:** None.
6. **Request headers:** Provider specific signature headers.
7. **Path parameters:** None.
8. **Query parameters:** None.
9. **Request body:** Vendor specific payload.
10. **Validation rules:** Signature MUST match computed HMAC.
11. **Business rules:** If SUCCESS -> Update PaymentStatus -> Confirm Order -> Commit Inventory. If FAILED -> Fail Payment -> Cancel Order if timeout.
12. **DB entities affected:** `PaymentWebhookEvent`, `PaymentTransaction`, `Payment`, `Order`, `InventoryReservation`.
13. **Transaction boundary:** Strict Transaction across Order and Payment updates.
14. **Idempotency:** Enforced via `externalEventId` stored in DB.
15. **Success response:** `{ "success": true, "message": "Acknowledged" }`
16. **Error responses:** `401 Invalid Signature`
17. **Error codes:** `UNAUTHORIZED_WEBHOOK`
18. **Pagination:** N/A
19. **Rate limiting:** 100/min / IP (Vendor IP whitelist).

### 3.4 Inventory Module (Admin)

**Endpoint:** `PATCH /api/v1/admin/inventory/:variantId`
1. **HTTP Method:** `PATCH`
2. **Endpoint path:** `/api/v1/admin/inventory/:variantId`
3. **Purpose:** Manual adjustment of inventory.
4. **Auth requirement:** Required.
5. **Required role:** `INVENTORY_MANAGER` or `SUPER_ADMIN`.
6. **Request headers:** `Authorization`
7. **Path parameters:** `variantId` (UUID)
8. **Query parameters:** None.
9. **Request body:** `{ "quantity": "number", "reason": "string" }`
10. **Validation rules:** Quantity >= 0.
11. **Business rules:** Adjust base quantity. Cannot adjust below `reservedQuantity`.
12. **DB entities affected:** `Inventory`, `AuditLog`.
13. **Transaction boundary:** DB Transaction required to check `reservedQuantity` constraint safely.
14. **Idempotency:** Not strictly required (state update).
15. **Success response:** Standard Success.
16. **Error responses:** `400 Cannot reduce below reservations.`
17. **Error codes:** `VALIDATION_ERROR`
18. **Pagination:** N/A
19. **Rate limiting:** Standard admin limits.

### 3.6 Returns Module

**Endpoint:** `POST /api/v1/returns`
1. **HTTP Method:** `POST`
2. **Purpose:** Customer initiates a return request.
3. **Auth requirement:** Required. **Required role:** `CUSTOMER`.
4. **Request body:** `{ "orderId": "uuid", "items": [{ "orderItemId": "uuid", "quantity": 1, "reason": "DAMAGED" }], "description": "string?", "evidenceUrls": ["string"] }`
5. **Business rules:** Order status must be `DELIVERED`. Items must not exceed original quantity. `returnedQuantity` check on `OrderItem`. Return window enforced by business rule.
6. **DB entities affected:** `Return`, `ReturnItem`, `ReturnEvidence`
7. **Transaction boundary:** Required.
8. **Idempotency:** Recommended.
9. **Error codes:** `INVALID_ORDER_STATE`, `NOT_FOUND`, `VALIDATION_ERROR`
10. **Rate limiting:** 3 requests / minute / user.

**Endpoint:** `GET /api/v1/returns` | `GET /api/v1/returns/:id`
1. **Auth:** Required. **Pagination:** Supported on list.
2. **Business rules:** Customer can only view their own returns.

**Endpoint:** `POST /api/v1/admin/returns/:id/approve`
1. **HTTP Method:** `POST` | **Auth:** Required | **Role:** `ORDER_MANAGER` or `SUPER_ADMIN`
2. **Purpose:** Admin approves return and triggers refund.
3. **DB entities affected:** `Return`, `Refund`, `OrderItem` (increment `returnedQuantity`).
4. **Transaction boundary:** Required (Return update + Refund insert must be atomic).
5. **Idempotency:** REQUIRED.
6. **Error codes:** `INVALID_ORDER_STATE`, `CONFLICT`

**Endpoint:** `POST /api/v1/admin/returns/:id/reject`
1. **HTTP Method:** `POST` | **Auth:** Required | **Role:** `ORDER_MANAGER` or `SUPER_ADMIN`
2. **Request body:** `{ "reason": "string" }`
3. **DB entities affected:** `Return`

### 3.7 Courier Webhook Module

**Endpoint:** `POST /api/v1/webhooks/courier/:provider`
1. **HTTP Method:** `POST`
2. **Endpoint path:** `/api/v1/webhooks/courier/:provider` (e.g., `/pathao`, `/steadfast`, `/redx`)
3. **Purpose:** Receive courier delivery status updates asynchronously.
4. **Auth requirement:** None (signature validated instead).
5. **Request headers:** Provider-specific HMAC signature headers.
6. **Validation rules:** Signature MUST match HMAC computed with provider secret.
7. **Business rules:** Map external status → internal `ShipmentStatus`. Update `Shipment` + `Order`. Create `ShipmentEvent`. Trigger customer notification via BullMQ.
8. **DB entities affected:** `ShipmentEvent`, `Shipment`, `Order`
9. **Transaction boundary:** Required (Shipment + Order atomic).
10. **Idempotency:** Enforced via event deduplication (check existing `ShipmentEvent`).
11. **Success response:** `{ "success": true, "message": "Acknowledged" }`
12. **Error codes:** `UNAUTHORIZED_WEBHOOK`
13. **Rate limiting:** 200/min / IP (Courier IP allowlist).

## 4. Appendices

### 4.1 API Dependency Map
```text
/api/v1/orders -> depends on -> /api/v1/cart, /api/v1/inventory, /api/v1/coupons, /api/v1/risk
/api/v1/payments -> depends on -> /api/v1/orders
/api/v1/returns -> depends on -> /api/v1/orders, /api/v1/shipments
```

### 4.2 Module-to-Endpoint Map (Summary)
*   **Auth:** `/auth/phone/send-otp`, `/auth/phone/verify-otp`, `/auth/email/send-otp`, `/auth/email/verify-otp`, `/auth/google`, `/auth/google/callback`, `/auth/admin/login`, `/auth/refresh-token`, `/auth/logout`
*   **Catalog:** `/products`, `/products/:slug`, `/categories`, `/brands`, `/age-groups`, `/skills`
*   **Customer:** `/wishlist`, `/wishlist/:productId`, `/addresses`, `/reviews`
*   **Checkout:** `/cart`, `/cart/items`, `/cart/items/:id`, `/orders`, `/orders/:id`, `/orders/:id/verify`, `/orders/:id/cancel`
*   **Payments:** `/webhooks/payment/:provider`
*   **Fulfillment:** `/shipments`, `/shipments/:id`, `/webhooks/courier/:provider`
*   **Support:** `/returns`, `/returns/:id`, `/refunds`, `/refunds/:id`
*   **Admin:** `/admin/inventory/:variantId`, `/admin/products`, `/admin/orders`, `/admin/customers`, `/admin/returns/:id/approve`, `/admin/returns/:id/reject`

### 4.3 Critical Business Rules
*   **Rule 1:** Client-provided prices, totals, and statuses are automatically ignored. The server computes everything from DB base values.
*   **Rule 2:** Inventory is guarded by physical `reservedQuantity` DB locks during checkout.
*   **Rule 3:** Orders triggered via COD run through the Risk Engine. High risk orders are blocked from COD.

### 4.4 Security Rules
*   RBAC enforced strictly at the route middleware level.
*   All webhooks (Payment, Courier) require cryptographically secure signature verification.
*   Tokens must not contain sensitive PII beyond ID/Role.

### 4.5 Transaction Requirements
*   `POST /orders` (Order Creation)
*   `POST /webhooks/payment` (Fulfillment)
*   `POST /returns/:id/approve` (Refund Initiation)
*   All require isolated PostgreSQL `BEGIN...COMMIT` blocks.

### 4.6 Idempotency Requirements
*   Mandatory for `POST /orders`, `POST /refunds`, `POST /payments`. Header: `Idempotency-Key`. Tracked in DB to prevent double-charging or duplicate orders.

### 4.7 OpenAPI/Swagger Implementation Notes
*   API must be documented using OpenAPI 3.0 specification.
*   Zod schemas should be used to auto-generate Swagger definitions using `zod-to-openapi`.
*   Swagger UI exposed at `/api-docs` (secured in production).

### 4.8 Known Gaps or Unresolved Decisions
*   **Notification Engine:** Notifications (SMS/Email/Push) are queue-driven via BullMQ. Synchronous delivery only for critical OTP flows.
*   **Advanced Risk Scoring:** ML model integration is deferred. Basic configurable rules engine used initially. Thresholds stored in `CODConfig` DB table.
*   **Payment Gateway Timeout:** If no webhook received within 30 minutes, a CRON job polls gateway status API and reconciles `Payment` + `Order` state.
*   **COD Config:** Risk thresholds, COD limits, and advance payment percentages are stored in the `CODConfig` DB table and configurable via admin API — not hardcoded in env vars.
*   **Courier Webhook Idempotency:** Deduplication via checking existing `ShipmentEvent` records before processing. No separate event ID table for couriers.
